# Execução com alta disponibilidade

Execute `docker compose -f compose.ha.yml up --build`. O ambiente cria duas réplicas do backend, dois gateways, três Redis, três Sentinels e PostgreSQL. Use `docker compose -f compose.ha.yml -p f1-ha up -d --build` para manter esse ambiente separado do Compose padrão. Se os dois estiverem ativos, use `F1_API_PORT`, `F1_ALT_API_PORT`, `F1_FRONTEND_PORT` e `F1_VIZ3D_PORT` para evitar conflito de portas. O 2D fica na porta 3000 e o 3D independente na 3001. Os gateways HTTP/WebSocket também ficam acessíveis nas portas 8000 e 8001. Os proxies das visualizações usam ambos os gateways; o acesso direto à API deve tratar falha de uma porta ou usar um balanceador externo. A sub-rede fixa 172.29.163.0/24 precisa estar livre.

Cada corrida tem um processo proprietário. Aproximadamente a cada segundo simulado, um checkpoint salva em Redis o estado do motor, clima e seus números aleatórios, estratégia e box, histórico dos controladores, poses, velocidades e juntas dos carros. Se a concessão do proprietário expirar, outra réplica pode adquirir uma nova concessão e recuperar o checkpoint. Cada publicação confere a concessão em uma transação Redis: um processo que perdeu a concessão deixa de publicar. A retomada envia o evento `race_recovered`, cujo `sim_ts` indica o ponto restaurado; o WebSocket aceita novamente ticks a partir desse instante. Os proxies 2D e 3D tratam o retorno no tempo.

O controlador por regras é o único controlador de corrida suportado pelo checkpoint. A retomada não é bit a bit: o cache de contatos interno do PyBullet não é exportado, então uma colisão em andamento pode evoluir de forma diferente. Dados e comandos de box aceitos depois do último checkpoint podem ser perdidos; o cliente deve observar `pit_request` no tick/snapshot e reenviar o pedido se necessário. Um checkpoint é uma serialização Python e pode se tornar incompatível após alterações de código ou dependências: finalize as corridas antes de atualizar a imagem. Mantenha o Redis na rede privada do Compose e configure `F1_CHECKPOINT_SECRET` igual em todas as réplicas. O backend confere a assinatura do checkpoint antes de carregá-lo. O valor padrão serve ao ambiente local. A comunicação entre réplicas não tem autenticação nem criptografia.

O Redis Sentinel promove uma réplica quando possível. A publicação aguarda até 90 segundos em falhas transitórias. A replicação é assíncrona: falhas podem perder escritas recentes e, sob partição, não há garantia de consenso forte ou de exclusividade absoluta. `min-replicas-to-write` reduz o risco, mas impede gravações se não houver uma réplica conectada. AOF e replicação não substituem backups. O Redis Pub/Sub fornece a difusão dos eventos; esta implementação não usa RabbitMQ ou Kafka.

O Compose é para desenvolvimento em um único host: a queda do próprio host ou do acesso à porta exposta não é coberta. As visualizações contam com dois gateways, mas cada frontend e cada porta externa ainda precisa de redundância por um balanceador ou orquestrador para alta disponibilidade real. Os três Sentinels precisam de quórum. A configuração e os volumes Sentinel são específicos da sub-rede do Compose.

O PostgreSQL importa os snapshots locais de circuitos, waypoints e pilotos na primeira inicialização. Se um snapshot não estiver incluído na imagem, o bootstrap busca a cópia versionada e valida seu hash. O backend usa o banco para consultas do catálogo e por temporada. Os SVGs dos layouts simuláveis são baixados em segundo plano e cacheados no PostgreSQL. O Compose padrão também usa PostgreSQL e permanece disponível para execução local sem Sentinel.

O Compose inicia uma instância do consumidor de IA e o Ollama. Na primeira inicialização o Ollama baixa o modelo `llama3.2` para o volume `ollama_data`. O consumidor acompanha os eventos das corridas no Redis Sentinel e publica `ai_suggestion` no canal da corrida; usa o piloto do usuário quando informado ou o primeiro piloto do grid. A interface atual ainda não exibe essas sugestões. `AI_INTERVAL_SECONDS` ajusta o intervalo em segundos simulados (padrão: 10).

Os espectadores são acompanhados por heartbeats no Redis, inclusive quando o WebSocket está em outra réplica. Uma perda de conexão tem prazo de reconexão antes de a corrida ser cancelada por falta de público. A queda simultânea de todo o Redis não tem garantia de retomada. O PostgreSQL deste Compose é uma instância única.

O consumidor de IA está fora deste Compose.
